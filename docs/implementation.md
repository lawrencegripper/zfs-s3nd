# Implementation Doc

## Development approach

Build this in a tight validation loop:

```text
write/adjust test rig
  -> implement smallest slice
  -> run local tests
  -> inspect failures/logs
  -> fix or improve observability
  -> repeat
  -> promote passing behavior into CI
```

The test rig comes first. The application should only grow behind executable tests that prove the ingest, catalog, storage, recovery, and validation paths work.

## Principles

- Use `pressly/goose` for SQLite migrations.
- Use `sqlc` for type-safe Go query generation from SQL.
- Tests should exercise the real network paths where practical: SSH, HTTP, SQLite, and S3-compatible object storage.
- Local development should not require Railway for the core loop.
- Railway-specific behavior should have a separate smoke/e2e layer.
- Every bug found manually should become a regression test.
- Failure handling is a product feature, not an afterthought.
- Use deterministic fixtures where possible, and capability-detect real ZFS support where needed.

## Test rig first

### Local services

Use Docker Compose for local dependencies:

1. **RustFS**
   - Open-source Rust S3-compatible stand-in for Railway Buckets.
   - Apache 2.0 licensed MinIO alternative.
   - Tests should use the same storage interface that production uses.

2. **App under test**
   - Go service exposing:
     - HTTP UI/API port
     - SSH ingest port
   - SQLite database mounted at a temporary test path.

3. **Optional privileged ZFS runner**
   - Only enabled when host/CI supports it.
   - Used for real `zfs send` / `zfs recv` tests.

Default local loop should work without real ZFS by using committed or generated byte-stream fixtures.

## Test layers

### 1. Unit tests

Run on every edit.

Coverage:

- SSH command parser
- Source/pool/dataset/snapshot name validation
- Source/pool/dataset identity mapping
- SSH key fingerprinting
- Object key generation
- Upload state machine
- Operation timeline state transitions
- Usage calculations
- Validation scheduler selection
- Restore-chain planning

Example commands:

```bash
go test ./internal/...
```

### 2. Integration tests

Run against SQLite and RustFS.

Coverage:

- Migrations apply cleanly
- Catalog transactions are atomic
- Storage adapter can write/read/list/delete chunk objects
- Manifest object is not treated as committed until catalog commit succeeds
- Completed upload creates snapshot and snapshot chunk rows
- Failed upload does not create committed snapshot row
- Reconciler cleans stale uploads and abandoned chunks/manifests
- Operations/events are appended for uploads, failures, retries, validation, and cleanup
- Same dataset path from different source/pool tuples does not collide

Example commands:

```bash
docker compose -f docker-compose.test.yml up -d rustfs create-bucket
go test ./test/integration/...
```

### 3. SSH ingest e2e tests

Run against a real app process.

Coverage:

- Unknown SSH key rejected
- Known SSH key accepted
- Shell access rejected
- Unknown exec command rejected
- No-command SSH session accepts a ZFS send stream on stdin
- Uploaded stream appears in bucket
- Catalog records source/pool/dataset/snapshot/bytes/checksum/status
- Duplicate snapshot rejected within same source/pool/dataset
- Same snapshot name accepted for different source or pool
- Incremental upload requires existing base in the same source/pool/dataset lineage

Example flow:

```bash
zfs send tank/photos@snap1 \
  | ssh -i test/fixtures/client_key -p 2222 truenas@localhost
```

For tests, fake stream bytes are acceptable for ingest behavior. Real stream validation belongs in validation tests.

### 4. Failure injection tests

These are critical.

Cases:

1. **Client disconnects mid-upload**
   - Start upload.
   - Send partial bytes.
   - Kill client connection.
   - Assert upload session becomes failed/stale.
   - Assert no committed snapshot exists.
   - Assert partial chunk objects are cleaned or marked for cleanup.

2. **App process dies mid-upload**
   - Start upload.
   - Kill app container/process.
   - Restart app.
   - Reconciler marks stale session failed.
   - Retry succeeds.

3. **Bucket write failure**
   - Inject storage adapter failure after N bytes/parts.
   - Assert clean failure state.
   - Assert retry succeeds.

4. **SQLite commit failure after object upload**
   - Complete object upload.
   - Force catalog transaction failure.
   - Reconciler detects orphan completed object or incomplete commit.
   - System either commits safely or quarantines object.

5. **Manifest/commit failure**
   - Simulate manifest write failure.
   - Simulate catalog commit failure after manifest upload.
   - Assert no snapshot is exposed as committed.
   - Assert chunks/manifests are either reconciled into a valid commit or quarantined for cleanup.

6. **Incremental chain failure**
   - Upload full.
   - Try incremental with missing base.
   - Try duplicate incremental snapshot.
   - Assert expected rejections.

### 5. Real ZFS tests

Capability-detected.

If ZFS tooling and privileges are available:

- Create temporary file-backed pool.
- Create dataset.
- Write test files.
- Snapshot.
- Run `zfs send` through SSH ingest.
- Download object from RustFS.
- Restore into separate pool/dataset.
- Verify files and snapshots.
- Repeat for incremental snapshot chain.

If unavailable, skip with a clear message.

### 6. Railway smoke tests

Run after Railway deploy.

Coverage:

- HTTP health endpoint responds.
- SQLite volume is writable.
- Railway Bucket credentials work.
- SSH TCP proxy accepts connections.
- Known test key can upload a small stream.
- UI/API shows the uploaded snapshot.
- Validation job can create a Railway Sandbox.

## Railway Sandbox validation rig

Production restore validation should use Railway Sandboxes.

### Sandbox job flow

1. App queues validation job.
2. Worker creates sandbox with short idle timeout.
3. Worker installs or uses checkpointed ZFS tooling.
4. Worker writes a validation script into sandbox.
5. Script downloads stream chain from Railway Bucket.
6. Script creates temporary file-backed ZFS pool.
7. Script runs `zfs recv` for full and incremental streams.
8. Script verifies expected datasets/snapshots.
9. Worker captures stdout/stderr/exit code.
10. Worker stores result in SQLite and optional logs in bucket.
11. Worker destroys sandbox.

### Sandbox implementation options

Start simple:

- Install tools at runtime in each sandbox.

Then optimize:

- Create a Sandbox template/checkpoint with ZFS tools preinstalled.
- Reuse checkpoint for faster validation startup.

### Sandbox failure handling

Validation job statuses:

```text
queued -> starting -> running -> passed
queued -> starting -> running -> failed
queued -> starting -> errored
queued -> starting -> timed_out
```

On failure:

- Keep logs.
- Keep sandbox id in job record while running.
- Destroy sandbox in `finally` path.
- Mark job retryable where appropriate.
- Retry transient sandbox/API/bucket failures with backoff.
- Do not retry deterministic restore failures indefinitely.

## Reference implementation notes from zfsbackup-go

`someone1/zfsbackup-go` is a client-side project, not the architecture we want, but it has useful design lessons:

- It splits ZFS send streams into ordered volumes/chunks rather than assuming one huge object.
- It writes manifests containing volume metadata, stream options, source volume, snapshot, incremental base, sizes, and checksums.
- It treats resumability as a manifest/chunk problem: completed chunks can be discovered and skipped if the same job is retried with matching options.
- It records both whole-stream bytes and stored bytes.
- It uses per-volume checksums and retries uploads with exponential backoff.
- It carefully validates that resumed jobs use matching options before trusting previous chunks.

Apply those lessons server-side:

- Our SSH server receives the stream, chunks it, uploads chunk objects, and writes a manifest.
- The catalog is authoritative, but the manifest should be self-describing enough to validate/restore without relying on fragile object naming.
- Interrupted SSH uploads in v1 still require the user to retry, but the internal format should make future partial-resume feasible.
- The reconciler should validate chunk rows against object existence, size, and checksum.
- Restore and validation should consume manifests and concatenate chunks in order.

## Core state machine

Upload sessions should be explicit.

```text
pending
  -> uploading
  -> writing_chunk
  -> committing_manifest
  -> committing_catalog
  -> complete

pending/uploading/writing_chunk/committing_manifest/committing_catalog
  -> failed
  -> aborted
```

Rules:

- Only `complete` sessions create committed snapshots.
- Chunk objects are never listed as valid backups without a committed manifest and catalog row.
- Final chunk and manifest objects are immutable.
- Snapshot names are unique per source/pool/dataset.
- Failed sessions are visible to the user with retry guidance.

## Build status and remaining work

Current build summary:

- Railway-hosted Go service with HTTP dashboard, SSH ingest, SQLite catalog on volume, and S3/Railway Bucket object storage.
- SSH public-key auth is managed from the dashboard; the web UI uses form-based login sessions, API routes use Bearer API tokens, and first-run setup is available when no admin password exists; `/healthz` remains public.
- Full and incremental ZFS send streams are stored as ordered chunk objects with plaintext DR manifests.
- Chunk objects are encrypted with XChaCha20-Poly1305 using a key derived from `STORAGE_ENCRYPTION_KEY` passphrase via Argon2id.
- Snapshot manifests include explicit format/version and encryption/KDF metadata.
- Upload failure/retry paths are covered with failure injection and E2E tests.
- Stale uploads are reconciled on startup and periodically while the service runs; SSH uploads fail after five minutes with no new bytes.
- Shutdown is drain-aware for SSH uploads: SIGTERM stops new SSH sessions, polls SQLite active upload sessions, logs source/pool/dataset/snapshot/bytes while waiting, and exits once no active uploads remain or `SHUTDOWN_GRACE_PERIOD` expires; Railway is configured with a 6-hour deployment drain window.
- Catalog backups can run in-process on a schedule and are surfaced on the dashboard.
- Admin dataset/snapshot pages include delete actions that enqueue durable cleanup operations; the in-process cleanup worker resumes queued/running work after restart and removes catalog rows plus associated manifest/chunk objects from object storage.
- Validation has a chain-aware scheduled core plus persisted job/status UI and an in-process hourly due-validation scheduler; true external restore validation is still outstanding. SSH uploads also trigger asynchronous single-stream post-upload validation that verifies the new stream/chunks and parent GUID relationship without re-reading the full ancestor chain.
- Commandless SSH upload is supported: when the client opens an SSH session with no exec command, the server treats stdin as a ZFS send stream, parses the DRR_BEGIN header, infers pool/dataset/snapshot, GUID lineage, raw/compressed flags, and finds the incremental base by GUID.
- Incremental chains are capped by `MAX_INCREMENTAL_CHAIN_DEPTH` (default 30). If an incremental would exceed the cap, the upload is rejected before chunks are stored and the client should send a full snapshot as a new anchor. The batch zvol uploader also uses `chain_depth` from `state` to choose a full anchor proactively.
- `restore-chain-to <snapshot-id> <zfs-target>` restores the full dependency chain by running `zfs recv` once per stored stream. `restore-stream <snapshot-id>` streams one stored snapshot; before incremental streams it writes the required parent to stderr, and after streams with children it writes the next restore command plus a remaining count.
- The zvol uploader script still exists as an optional batch helper: it discovers committed remote snapshots via SSH `state`, selects incremental bases without local state or direct S3 access, relies on server-enforced throughput limits, logs to a file, and auto-selects raw sends for encrypted zvols.
